# Journal - 2026-03-14

## Summary

Today the ecommerce data platform moved from a reporting-first posture into a clearer control-system path.

The key result was not a new dashboard. It was a tighter architectural bridge from the current PDD workbook ingestion foundation toward a first narrow decision layer.

## What was completed

### 1. Remote operating mode was proven
The OpenClaw ACPX bridge was configured and verified so EDP Commander can now launch headless OpenCode runs on the Mac mini from Telegram.

This matters because it means architecture, repo-editing, and implementation coordination can continue while away from the desk.

### 2. Repo-aligned foundation docs were added
A documentation cleanup and alignment pass produced a stronger repo foundation:
- `docs/data_model_v1.md`
- `docs/workbook_import_contracts.md`
- `docs/architecture_status.md`

These docs corrected the center of gravity of the project:
- PDD workbook ingestion is the current core
- canonical daily facts matter more than generic ecommerce-order abstractions
- reporting views are downstream, not architecture core

### 3. The control-system destination became much clearer
Boss direction was clarified significantly.

The target is not:
- a dashboard
- a normal report system

The target is:
- a shop-differentiated operating control system
- SPU as the decision unit
- SKU as the execution lever
- 7-day trends as the basis for judgment
- operator-facing action output such as must-do, prohibited, and weekly-priority actions

This was the most important product clarification of the day.

### 4. Minimum pre-decision-layer docs were created
A second OpenCode pass produced the minimum bridge docs needed before decision-layer work:
- `docs/ingestion_hardening_requirements.md`
- `docs/spu_sku_operating_bridge.md`
- `docs/seven_day_trend_signal_foundation.md`
- `docs/decision_layer_readiness_gate.md`
- `docs/pdd_control_logic_v1_1_core_build_plan.md`

These documents established the correct stance:
- do not jump directly into a giant decision engine
- first finish the last data-prep layer
- then build a narrow control-system release

### 5. Trend and SPU support views were added to schema
`sql/schema.sql` was updated with low-risk reporting views that support the next control-layer step:
- `reporting.vw_pdd_spu_day_derived`
- `reporting.vw_pdd_shop_7d_trend`
- `reporting.vw_pdd_spu_7d_trend`
- `reporting.vw_pdd_sku_execution_lever`

The SPU 7-day trend view was later tightened so churn / last-week-only rows are handled more safely.

## What was learned

### Product lesson
The project is no longer best described as “build a dashboard on top of PDD data.”

A more accurate framing is:
- build a PDD-first ecommerce control foundation
- then use that foundation to produce operator-facing decisions

### Architecture lesson
The current raw -> staging -> canonical pattern still holds.

The correct next move is not broad new source expansion or dashboard growth. It is:
1. ingestion hardening
2. SPU/SKU bridge tightening
3. 7-day trend signal layer
4. first narrow decision-layer design

### Modeling lesson
SPU is now the most important unresolved bridge.

We have strong:
- shop-day facts
- SKU-day facts

But we still need careful handling of:
- SPU proxying via `product_id`
- confidence labeling where signals are estimated rather than directly sourced

## Current project state at end of day

- source/platform focus: **PDD only**
- ingestion posture: **workbook-first**
- canonical facts: **shop-day + SKU-day**
- reporting posture: **downstream / temporary inspection layer**
- new strategic destination: **operator-facing control system**
- SPU handling: **proxy-ready, not fully canonicalized**
- trend layer: **defined and scaffolded via SQL views**
- remote operating mode: **working from Telegram via ACPX/OpenCode**
